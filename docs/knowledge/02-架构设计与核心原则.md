# 架构设计与核心原则

## 1. 总体架构

```text
Vercel / API Request Boundary
          ↓
     Runtime Contract
          ↓
 Durable Agent Runtime
 ┌────────┼──────────┐
 │        │          │
PostgreSQL Redis    Worker
 │
 ├─ Run / Turn
 ├─ Tool Execution
 ├─ Permission
 ├─ Idempotency
 ├─ Outbox
 ├─ Checkpoint
 └─ Recovery
          ↑
     Adapter Contract
          ↑
AgentScope / LangGraph / Eino / Mastra
```

## 2. 权威数据边界

PostgreSQL 是 authoritative durable state。内存对象只能作为执行中的缓存或 reference implementation，不得作为跨请求、跨 Worker 的最终真相。

Redis 的职责是可选异步协调、缓存或队列设施；即使 Redis 不可用，核心 durable state 也必须能够解释当前 Agent 状态。

## 3. Runtime Contract 原则

Runtime Contract 是应用层唯一稳定入口。至少需要覆盖：

- 创建 Run
- 获取 Run 状态
- Turn 生命周期
- Tool execution
- checkpoint
- recovery
- cancellation

状态机必须显式定义合法迁移，禁止通过字符串或框架隐式行为改变生命周期。

## 4. Tool Execution 安全边界

工具执行流程必须可以抽象为：

```text
请求
 ↓
身份/租户上下文
 ↓
Permission
 ↓
Idempotency lookup / claim
 ↓
实际 Tool
 ↓
持久化结果
 ↓
Outbox
 ↓
提交
```

其中 permission 是“能不能做”，idempotency 是“同一业务动作是否只能产生一次效果”。两者不能互相替代。

## 5. Outbox 事务原则

当一次 Tool execution 同时产生业务结果和需要发布的事件时，二者必须位于同一明确事务边界：

```text
BEGIN
  write result
  write idempotency result
  write outbox
COMMIT
```

Publisher 在事务之外异步工作。Publisher 崩溃不应回滚已经提交的业务结果；重复发布必须由 delivery/idempotency 语义吸收。

## 6. Recovery 原则

Recovery 是一个独立 durable workflow，而不是请求失败后的简单重试。

候选任务进入 recovery 后需要：

1. durable discovery
2. 原子 claim
3. lease ownership
4. lease renewal
5. crash 后 expired lease reclaim
6. retry/backoff 或 terminal failure
7. 最终状态落库

claim 使用 PostgreSQL 锁语义时必须避免多个 Worker 同时取得同一候选任务。

## 7. Lease / Fencing 原则

只判断 lease 是否存在是不够的。恢复任务应具有 owner/token 等可验证身份，使旧 Worker 在 lease 失效后不能继续提交状态。

所有完成、renew、failure 等写操作都应带 owner/token guard。

## 8. Adapter 原则

Adapter 只能把 Framework 的能力映射到 Runtime Contract，不得把 Framework 特有 API 渗透到 application contract。

例如：

```text
Framework node / graph / agent
          ↓
Adapter
          ↓
Runtime Contract
          ↓
Durable Runtime
```

因此即使未来替换 Framework，Run、Tool、Permission、Recovery 等平台语义也不应改变。

## 9. Deployment Boundary 原则

Vercel/API：

- validate
- authenticate
- invoke Runtime Contract
- query durable state
- return accepted/completed

Worker：

- long-running execution
- recovery
- lease coordination
- outbox publishing
- concurrency control

这使请求生命周期与 Agent 生命周期解耦。

## 10. Benchmark 原则

Benchmark 必须测试失败模式而非只测试成功路径。16 个场景覆盖：

- Permission：B01–B03
- Idempotency：B04–B05
- Outbox：B06–B08
- Crash/Recovery：B09–B13
- Retry/Failure/Concurrency：B14–B16

四个 Adapter × 16 个案例 = 64 个组合。

## 11. 核心不可变不变量

### I1 Permission
未经授权的 Tool 不得产生外部效果。

### I2 Idempotency
同一个有效业务动作重复提交不得产生第二次业务效果。

### I3 Outbox Atomicity
已提交业务结果必须具有对应 Outbox 事实；未提交事务不得产生孤儿发布。

### I4 Recovery Safety
Worker 崩溃后重新执行不得重复业务效果。

### I5 Lease Ownership
无有效 lease owner/token 的 Worker 不得完成 recovery 状态迁移。

### I6 Framework Neutrality
Application 不得依赖具体 Agent Framework 的执行细节。

### I7 Request Independence
请求结束不能导致 durable Agent execution 失去恢复能力。

## 12. 设计成熟度判断

架构层面目前已经形成可继续扩展的核心闭环，但“真实 PostgreSQL recovery + 真实 Framework SDK + 真实并发 worker + hard benchmark gate”仍是从参考架构迈向生产平台的关键一步。
