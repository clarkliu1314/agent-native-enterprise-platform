# 正式细化阶段与规格演进

## 1. 从方向到可执行规格

项目进入正式细化阶段后，重点从“选什么技术”转为“如何证明系统正确”。核心变化是把架构原则转成 contract、failure mode、SQL assertion、expected result 和 failure criteria。

## 2. Runtime Contract 细化

首先定义稳定的应用契约，再实现内存参考版本。契约测试覆盖 Run creation、合法状态迁移、checkpoint/recovery、cancellation 和 invalid transition。

这个阶段确立了：先定义行为，再写实现；Framework 不参与平台状态机定义。

## 3. Permission / Idempotency / Outbox 规格

### Permission

明确 allow、deny、scope mismatch、default deny。测试必须证明被拒绝的 Tool 没有业务副作用。

### Idempotency

明确 duplicate、conflict、replay、single-flight、tenant/tool scope。特别强调“同一个 key”不能简单理解成全局字符串，而必须具有业务 scope。

### Outbox

明确 atomic commit、publish retry、duplicate delivery。业务事务和 Outbox record 的原子性由数据库保证，Publisher 本身不拥有业务真相。

## 4. Crash Recovery 规格

恢复规格进一步拆成多个 crash point：

- claim 后崩溃
- tool 执行期间崩溃
- result 已保存但 outbox 尚未完成
- outbox 已提交但 worker 尚未 ack
- lease 过期后 reclaim
- retryable failure
- terminal failure
- concurrent workers

每个场景都需要明确初始状态、故障点、恢复动作、最终数据库状态和业务效果次数。

## 5. 16-case Benchmark 规格化

最终形成 16 个 Benchmark Case：

| 编号 | 主题 |
|---|---|
| B01 | permission allow |
| B02 | permission deny |
| B03 | permission scope mismatch |
| B04 | idempotency duplicate |
| B05 | idempotency conflict |
| B06 | outbox atomic commit |
| B07 | outbox publish retry |
| B08 | duplicate delivery |
| B09 | crash after claim |
| B10 | crash during tool |
| B11 | crash after result before outbox |
| B12 | crash after outbox before ack |
| B13 | expired lease reclaim |
| B14 | retryable backoff |
| B15 | terminal failure |
| B16 | concurrent workers |

每个 Case 必须包含：fixture、initial state、Mock LLM/Tool、精确操作步骤、SQL assertions、expected result、failure criteria、invariants、adapters。

## 6. 四 Adapter 统一测试规格

每个 Case 都绑定：

- AgentScope
- LangGraph
- Eino
- Mastra

因此 Benchmark matrix 固定为 16 × 4 = 64。Adapter 不能自行修改测试语义。

## 7. Deployment Boundary 规格

Vercel boundary 细化为：

- POST request validation
- agentId/input validation
- Runtime Contract invocation
- accepted/completed response
- provider-neutral LLM Gateway
- fail-closed configuration
- 静态禁止 recovery-worker、recovery-store、outbox-publisher 等 Worker-only 依赖进入 API handler

## 8. Local Environment 规格

Docker Compose 只提供已经有真实实现的基础设施：PostgreSQL、Redis、migration/seed、worker smoke、benchmark smoke。避免为满足“本地一键启动”而创建架构上不存在的 fake API 或 fake model service。

## 9. CI 规格

CI 从普通 unit tests 逐渐升级为：

1. typecheck
2. package export/packaging contract
3. full tests
4. API typecheck/build
5. deployment boundary safety
6. Compose smoke
7. Benchmark artifact
8. 最终 Benchmark hard gate

当前前七类已有较完整基础，最后的独立 hard gate 是下一阶段的重要强化。

## 10. 规格阶段形成的工程原则

- 先 failure mode，再 implementation。
- 每个安全性质都必须有机器断言。
- deterministic test 可以作为开发阶段基线，但不能冒充真实基础设施验证。
- 参考 Adapter 可以用于 contract development，但不能标记为真实 SDK integration。
- 文档必须同时说明“目标架构”和“当前实现”。
