# 正式编码实现阶段与工程演进

## 1. 实现方法

正式编码遵循 TDD：RED → 验证失败 → 最小实现 → GREEN → 重构/集成 → CI 验证。这个流程不是形式要求，而是用于防止架构文档与代码脱节。

## 2. 第一阶段：Runtime Contract

先写生命周期 contract tests，再建立类型和最小实现。随后加入 reference runtime，用于验证状态机、checkpoint、recovery、cancellation。

## 3. 第二阶段：Durable Persistence

PostgreSQL 成为 durable system of record。实现 Run store、Tool execution persistence、Idempotency 和 Outbox 等数据库能力，并把数据库 integration tests 纳入 CI PostgreSQL service。

后续修复还强化了 workspace package exports，避免源码路径测试通过但 package root 无法消费的问题。

## 4. 第三阶段：Tool Runtime Safety

ToolExecutionService 成为 Permission、Idempotency、实际 Tool execution 和结果持久化之间的安全边界。

后续演进增加了：

- tenant/tool scoped idempotency
- ordered execution
- single-flight
- result replay
- 明确 result + outbox transaction boundary
- execution safety boundary documentation

## 5. 第四阶段：Recovery

RecoveryCoordinator 和 PostgreSQL RecoveryCandidateStore 逐步形成生产级 primitive：

- candidate discovery
- atomic claim
- owner/token lease
- lease renewal
- expired reclaim
- durable failure record
- retryable/final classification
- bounded exponential backoff

这里的关键工程经验是：恢复逻辑必须独立于 HTTP request 生命周期。

## 6. 第五阶段：Benchmark

Benchmark 从 contract-only 定义逐渐升级为可执行 scenario runner。当前已经形成：

- 16 个 Case
- 4 个 Adapter
- 64 个组合
- 统一 `BenchmarkRunner.run()` / `runAll()`
- machine-readable JSON artifact
- B01–B16 deterministic scenario executor

B09–B16 的确定性实现实际调用/模拟平台核心安全组件，用于先验证业务语义，再逐步替换为真实 PostgreSQL/concurrency fixture。

### Run #218 / #225

## 9. 当前实现分类

| 分类 | 含义 |
|---|---|
| 已实现/已验证 | 代码存在且 CI 有证据 |
| deterministic-only | 语义已验证，但基础设施仍为确定性 fixture |
| production primitive | 已按真实持久化/事务/lease 模型实现，可作为生产核心组件 |
| reference adapter | 用于统一契约开发，不代表真实 SDK 集成 |
| production integrated | 真实外部系统、真实并发或真实 SDK 已接入并验证 |

后续所有状态报告必须使用这套分类，避免“测试通过”被误解为“生产集成完成”。
