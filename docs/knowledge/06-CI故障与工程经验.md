# CI 故障与工程经验

## 1. 总原则

CI 是架构反馈系统，不只是最后一道“代码有没有编译”的检查。每一次失败都应判断它暴露的是代码 bug、测试 fixture bug、package boundary bug、架构假设错误还是验证层级不足。

## 2. 典型故障模式

### Package boundary

Run #68、#83、#194、#202、#214 等问题共同说明：workspace package 的 root entrypoint 是真实系统边界。必须同时检查 `main`、`types`、`exports` 和 workspace dependency resolution。

### Test double drift

Run #62、#112、#225 表明测试 double 不是“随便写一个 mock”。它必须持续满足生产接口契约，否则测试本身会成为噪声来源。

### Fixture semantics

Run #138、#140、#209 表明 integration fixture 必须准确表达数据库参数、lease ownership 和 external effect 语义。为了让测试通过而放宽生产类型或删除约束，会掩盖真正风险。

### Benchmark completeness

Run #216 证明“案例定义完成”不等于“执行器完成”。Benchmark 必须有从 specification 到 executable runner 的完整链路。

## 3. 推荐故障处理流程

```text
CI failure
   ↓
定位最小失败测试
   ↓
判断是产品代码 / 测试 / packaging / 环境 / 架构假设
   ↓
如果是缺失行为：先补 RED test
   ↓
最小修复
   ↓
focused verification
   ↓
full suite
   ↓
CI
   ↓
记录根因与防回归措施
```

## 4. 不允许的修复方式

- 删除失败测试。
- 把断言改宽以“适配”错误实现。
- 用 `any` 绕过真实类型问题。
- 把真实依赖替换成无法表达真实语义的 fake。
- 在 API 层偷偷加入 Worker 行为来绕过部署边界。
- 只验证本地而不让 CI 重现。

## 6. 下一阶段 CI 强化

CI 应从“所有 tests 通过”进一步升级到“所有安全不变量通过”：

- 独立 Benchmark job
- 64 matrix completeness check
- permission invariant gate
- idempotency invariant gate
- outbox invariant gate
- real PostgreSQL recovery gate
- real concurrent worker gate
- real Adapter integration gate
- artifact retention

## 7. 工程知识沉淀规则

每次重要失败至少记录：

1. Run ID
2. 失败症状
3. 最小复现
4. 根因
5. 修复 commit
6. 回归测试
7. CI 最终结果
8. 应避免再次发生的架构/工程原则
