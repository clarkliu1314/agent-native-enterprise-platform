# 技术选型与决策记录

> 本文沉淀项目早期技术选型阶段形成的关键判断，作为后续架构评审和技术变更的基线。若未来改变任何核心选择，应补充“变更原因、替代方案、迁移成本、回滚方式”。

## 1. 项目目标的技术化定义

本项目不是在传统企业软件上外挂一个聊天机器人，而是建设一个可以承载长期运行、可恢复、有副作用工具调用、可审计 Agent 的企业级底座。核心目标因此从“让模型调用工具”升级为“让 Agent Run 成为可持久化、可恢复、可治理的软件执行单元”。

由此形成第一原则：**Agent Framework != Agent Runtime**。

Framework 负责模型编排、节点/图/Agent 能力；Runtime 负责企业系统真正关心的 durable execution、权限、幂等、Outbox、Recovery、Cancellation、审计和状态真相。

## 2. Agent Framework 选型结论

候选方向包括 AgentScope、LangGraph、Eino、Mastra。没有选择其中任意一个作为平台核心，而是建立统一 Adapter Contract。

### 原因

1. 框架生态和 API 会变化，不能成为企业业务 API 的永久依赖。
2. 四个框架的执行模型不同，直接把其中一个作为 Runtime 会把其他框架降级成二等公民。
3. Durable execution、permission、idempotency、outbox、recovery 属于平台能力，不应该由模型编排框架隐式决定。
4. 统一 Benchmark 才能比较框架，而不是比较不同业务实现。

### 结论

```text
Application
   ↓
Runtime Contract
   ↓
Durable Agent Runtime
   ↑
Adapter Contract
   ↑
AgentScope / LangGraph / Eino / Mastra
```

## 3. PostgreSQL 选型

PostgreSQL 被定义为 durable system of record。

选择原因：

- 事务语义成熟，适合状态、结果、幂等记录、Outbox、lease 等需要一致性的对象。
- `FOR UPDATE SKIP LOCKED` 适合 Worker claim 和并发任务分配。
- SQL assertions 便于 Benchmark 对 durability 属性做机器验证。
- 本地 Docker、CI service、云托管方案成熟。

Redis 的定位是可选异步基础设施，而不是权威状态存储。

## 4. Outbox 选型

业务状态与“需要发送的事件”必须拥有清晰的事务边界。直接在业务事务中调用外部消息系统会产生经典 dual-write 风险，因此采用 transactional Outbox：

```text
业务状态变更
      +
Outbox record
      ↓
同一事务提交
      ↓
Publisher 异步发布
      ↓
消费侧幂等
```

这个选择同时服务于 crash recovery、event delivery 和审计。

## 5. Idempotency 选型

任何具有外部副作用的 Tool 都必须通过平台执行安全边界，而不能要求每一个 Agent Framework 自己实现幂等。

关键判断：

- idempotency key 必须有明确 scope。
- 当前实现进一步覆盖 tenant/tool scope，避免不同租户或不同工具错误共享幂等记录。
- duplicate request 应 replay 已提交结果，而不是重新制造外部效果。
- 并发重复请求需要 single-flight 或等价数据库保护。

## 6. Crash Recovery 选型

恢复不是简单的“失败后再调用一次”。必须从 durable state、idempotency record、checkpoint 和 lease 推导下一动作。

恢复机制选择：

- durable candidate discovery
- `FOR UPDATE SKIP LOCKED` claim
- lease owner/token
- lease renewal
- expired lease reclaim
- retry/backoff
- terminal failure classification

这样 Worker 崩溃后可以由另一 Worker 接管，同时防止旧 Worker 在恢复后继续提交业务效果。

## 7. Vercel 选型边界

Vercel 适合作为 Web/API request boundary，但不适合作为 durable execution coordinator。

因此：

**允许：** 认证、参数验证、调用 Runtime Contract、读取 durable state、返回 accepted/completed。

**禁止：** 长时间 Agent execution、Recovery lease、Outbox publisher、Worker coordination、权威内存状态、request-lifetime-dependent execution。

这不是部署偏好，而是执行语义的边界。

## 8. Docker Compose 选型

Compose 用于本地复现真实基础设施边界：PostgreSQL、Redis、migration/seed、worker smoke、benchmark smoke。没有为了“看起来完整”而加入假的 LLM、假的 durable API 或假的第三方服务。

原则是：**只模拟外部不可控依赖，不伪造平台核心语义。**

## 9. TypeScript + pnpm + Vitest

TypeScript 用于统一契约、类型安全和多 package workspace；pnpm 用于 workspace 管理；Vitest 用于快速 contract/unit/integration tests。

工程上进一步形成 workspace package exports 约束，防止测试中能通过源码路径访问、但真实消费者无法通过 package root import 的问题。

## 10. Benchmark-first 的选型原则

平台不是以“代码量”判断成熟度，而以可重复的安全性质验证判断成熟度。因此从设计阶段就确定：

- 16 个核心案例
- 4 个 Adapter
- 64 个 case-adapter 组合
- Permission / Idempotency / Outbox 三类 invariant
- fixture、初始状态、Mock LLM/Tool、精确步骤、SQL assertions、expected result、failure criteria

## 11. 明确不采用的方向

### 不采用：Framework 直接成为 Runtime

会造成框架锁定、跨框架语义不一致和业务 API 污染。

### 不采用：Redis 作为权威状态库

Redis 适合作为异步/缓存设施，但核心 durable state、幂等、Outbox 和 recovery lease 需要数据库事务语义。

### 不采用：Vercel Function 持有长生命周期 Worker 状态

请求生命周期不应成为 Agent 生命周期。

### 不采用：Benchmark 只测 happy path

企业级 Agent 最危险的不是正常路径，而是 crash、retry、duplicate delivery、concurrency、permission boundary。

### 不采用：为 CI 制造“绿色假服务”

CI 应验证真实的数据库、package exports、request boundary 和 benchmark contract，而不是用 mock 把架构问题隐藏起来。

## 12. 后续变更原则

未来如果考虑更换数据库、队列、部署平台或 Agent Framework，必须先证明不会破坏以下不变量：

1. Runtime Contract 独立于 Framework。
2. 外部副作用 Tool 默认受 Permission + Idempotency 双重约束。
3. 状态与 Outbox 的提交边界明确。
4. Recovery 可从 durable state 独立完成。
5. API request lifetime 不决定 Agent execution lifetime。
6. 同一 Benchmark 能比较所有 Adapter。
